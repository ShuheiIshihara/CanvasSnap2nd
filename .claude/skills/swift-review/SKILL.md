# swift-review — 観点別分割コードレビュー

CanvasSnap2nd の差分を3つの観点に分解し、それぞれ専任のサブエージェントにレビューさせ、結果を統合して Markdown レポートを出力する。

**このスキルはレビューのみを行う。コードの修正は一切しない。** 修正が必要な場合はレポートを提示した上で、開発者に次のアクションを尋ねること。

## 手順

### 1. レビュー対象の差分を確定する（重要）

**対象の確定は必ずこのスキル側で1回だけ行い、確定した結果を各サブエージェントに明示的に渡す。** サブエージェントに `git diff` から独自に判断させると、3体が別々の範囲を見てレポートが噛み合わなくなる。

- 引数にコミット参照（ハッシュ、`HEAD~n`、タグ、ブランチ名）が渡された場合 → その差分。
  - 単一コミット: `git diff <ref>^ <ref>`
  - 範囲指定（`a..b`）: `git diff a b`
- 引数がない場合 → `git diff --staged`。
  - staged が空なら、unstaged に変更があるかを確認し、**開発者に「unstaged をレビューするか」を確認してから**進む。黙って切り替えない。
  - 作業ツリーもクリーンなら「レビュー対象の変更がありません」と伝えて終了する。

確定したら、変更ファイル一覧を取得しておく:

```bash
git diff --name-only <確定した範囲>
```

Swift ファイルが1つも含まれない場合は、その旨を伝えて開発者に続行を確認する。

**あわせて直近のコミット件名も取得する**（3体が各自 `git log` を叩く重複を避けるため、ここで1回だけ取得して各エージェントに配る）:

```bash
git log -6 --format='%h %s' <確定した範囲の起点>
```

これは「直前のコミットで除去・修正したものが、この差分で再び混入していないか」を各観点に照合させるための材料。今回のようなケース（直前コミットで個人名を除去したのに新規ファイルで再混入）は、差分単体しか見ないエージェントの構造的な死角になるため必須。

### 2. 3観点のサブエージェントを並列で起動する

以下の3体を **1つのレスポンス内でまとめて Agent ツール呼び出しする**（並列実行）。`run_in_background` は指定せず、全員の結果が揃うのを待つ。

| subagent_type | 担当観点 |
| --- | --- |
| `review-correctness` | ロジック誤り、並行性、クラッシュ要因、async/await、リーク、境界計算 |
| `review-architecture` | protocol 境界、Coordinator 経由、AppSettings、層の分離、重複、過剰抽象、死んだコード |
| `review-testing` | 正常系・異常系・境界値の充足、テスト分離、命名、アサーション品質 |

各エージェントへの prompt には必ず次を含める:

- **確定した差分範囲を再現できる具体的な git コマンド**（例: `git diff --staged`、`git diff abc123^ abc123`）
- 変更ファイルの一覧
- **手順1で取得した直近コミット件名の一覧**（そのまま貼る）と、「これらの意図に反する変更がないか照合すること」の指示
- 「担当観点以外は指摘しないこと」の再確認
- 出力は自エージェント定義の形式に従うこと

なお `review-correctness` のみ `model: opus` で動く（並行性・ライフサイクル・失敗経路の構成といった開放的な推論を要するため）。他2体は規約との照合が中心なので `sonnet` のまま。

### 3. 結果を集約する

3体のレポートを受け取り、次のルールで1本にまとめる。

- **重複の統合** — 同一箇所への複数観点からの指摘は1項目にまとめ、どの観点から挙がったかを併記する。
- **矛盾は両論併記** — 観点間で結論が食い違う場合（例: 一方が「protocol 化すべき」、他方が「過剰な抽象」）、**どちらかに裁定せず両方の主張と根拠を並べて提示し、判断は開発者に委ねる**。これは意図した設計であり、勝手に一方を削らないこと。
- **並び順** — 重大度（高 → 中 → 低）順。同一重大度内では観点順（正誤性 → アーキ → テスト）。
- **サブエージェントの結果を鵜呑みにしない** — 明らかに事実誤認の指摘（存在しない関数への言及、既に対応済みの内容）は、該当ファイルを Read で確認した上で落とす。落とした場合はレポート末尾の「除外した指摘」に理由付きで1行残す。

### 4. Markdown レポートを出力する

`docs/reviews/` に以下の命名で書き出す（ディレクトリがなければ作成）:

```
docs/reviews/YYYY-MM-DD-<対象>.md
```

`<対象>` は staged なら `staged`、コミット参照なら短縮ハッシュ等。同名が既にある場合は末尾に `-2`, `-3` と連番を付け、既存ファイルを上書きしない。

レポートの構成:

```markdown
# コードレビュー結果

- **対象**: `git diff --staged`（または対象コミット）
- **実施日**: YYYY-MM-DD
- **変更ファイル**: N件
  - `path/to/File.swift`
- **サマリ**: 高 N件 / 中 N件 / 低 N件

---

## 重大度: 高

### 1. 見出し
- **観点**: 正誤性 / アーキテクチャ / テスト網羅（複数可）
- **箇所**: `path/to/File.swift:123`
- **問題**:
- **失敗シナリオ / 影響**:
- **修正案**:

## 重大度: 中
（同上）

## 重大度: 低
（同上）

---

## 判断が分かれた指摘（要開発者判断）

### 見出し
- **箇所**: `path/to/File.swift:123`
- **A案（観点X）**: 主張と根拠
- **B案（観点Y）**: 主張と根拠
- **論点**: 何を基準に決めるべきか

---

## 観点別サマリ

| 観点 | 高 | 中 | 低 | 総評 |
| --- | --- | --- | --- | --- |
| 正誤性 | | | | |
| アーキテクチャ・設計 | | | | |
| テスト網羅 | | | | |

---

## 除外した指摘
- `path/to/File.swift:12` の「〜」— 理由
```

指摘がゼロの観点は「問題は検出せず」と明記する。無理に指摘を捻り出さない。

### 5. 開発者に報告する

チャット上では**レポートの全文を貼らず**、以下だけを返す:

- 出力したレポートのファイルパス
- 重大度別の件数
- 重大度「高」の項目の見出しのみ（箇条書き）
- 判断が分かれた項目がある場合はその件数と論点の要約

その上で「修正に進むか、レポートを読んで判断するか」を尋ねる。**このスキルは修正を行わない。**

## 注意

- 開発者への応答はすべて日本語。識別子・パス・コードはそのまま英語で残す。
- レポートは commit しない。commit は `git-commit` スキルの担当。
