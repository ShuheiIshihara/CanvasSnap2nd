## １．概要

本ドキュメントは、Swift + SwiftUIで開発するmacOS向けスクリーンショットアプリの要件を定義する。

### 1.1 プロジェクト目的

macOS上で動作するスクリーンショットツールを開発する。グローバルホットキーにより、アプリがバックグラウンドにあっても素早くキャプチャを実行できることを目指す。あわせて、Swift/SwiftUIのmacOSアプリ開発スキルの習得をトレーニング目的とする。

### 1.2 技術方針の変更経緯

本プロジェクトは当初C# + Avalonia UIでの開発を予定していたが、以下の理由からSwift + SwiftUIに方針変更した。

- macOS専用アプリに対して、Avaloniaを介したP/Invokeは間接的で複雑さが大きい
- ScreenCaptureKit（Apple公式フレームワーク）を直接使用することでキャプチャ実装が大幅に簡素化される
- グローバルホットキー、メニューバー常駐などのmacOS固有機能をネイティブAPIで直接実装できる
- macOS 26のLiquid Glassデザインが自動適用され、システムと統一感のあるUIが得られる
- Swift/SwiftUIスキルはiOSアプリ開発（BusSchedules等）にも直接活用できる

### 1.3 スコープ

| 区分 | 内容 |
|------|------|
| スコープ内 | 全画面キャプチャ、範囲選択キャプチャ、ウィンドウ指定キャプチャ、ファイル保存（PNG/JPEG）、グローバルホットキー |
| スコープ外 | プレビュー表示、クリップボードコピー、注釈機能、動画キャプチャ、Windows/Linux対応 |

| ID | 要件 | 詳細 |
|----|------|------|
| FR-024 | 対応言語 | 日本語および英語に対応する。将来的に他言語を追加可能な構成とする |

| FR-026 | UI文字列の対象範囲 | 設定画面・メニューバー・権限リクエストダイアログ等、ユーザーが目にする全UI文字列を翻訳対象とする |
| FR-027 | ファイル名パターン | 「Screenshot」等の固定プレフィックス文字列は言語に依存しない（ファイルシステム互換性のため英語固定） |

#### 実装方針

**String Catalog（.xcstrings）を使用する**

Xcode 15以降の標準機能。従来の `.strings` ファイルの進化版で、Xcode上のGUIで多言語管理が可能。
- `File > New > File... > String Catalog` で `Localizable.xcstrings` を作成
- プロジェクト設定で日本語・英語の2言語を追加
- SwiftUIの `Text("...")` に渡した文字列は自動的に翻訳対象として抽出される

**キー命名規則**

日本語をキーとして使用する（例: `"保存先ディレクトリ"`）。理由：
- コード可読性が高く、日本語環境でのプライマリ言語として直感的
- 小〜中規模アプリでの一般的な実装パターン
- 制約: キー（日本語原文）を変更すると各翻訳も再設定が必要

**言語選択肢の表記方針（ネイティブ表記 / autonym）**

UI業界のベストプラクティスに従い、**言語選択肢は各言語のネイティブ表記で固定**し、翻訳対象外とする。

| 選択肢の内部値 | 表示（UI言語に関わらず固定） |
|---------------|---------------------------|
| `.system` | システム設定に従う / System Default（※この項目のみUI言語で翻訳） |
| `.japanese` | 日本語 |
| `.english` | English |

理由：
- 英語話者UIで「Japanese」と表示しても日本語話者は自言語を認識できないケースがある。逆も同様
- 各言語話者は自分の言語をネイティブ表記（日本語なら「日本語」、英語話者なら「English」）で最も素早く認識できる
- macOSシステム設定、Apple製アプリ、その他多くのメジャーアプリがこの方式を採用
- 参考: W3C、Nielsen Norman Group等のi18nガイドラインで推奨されている方式

**ラベル自体（「表示言語」）はUI言語で翻訳する**

- 日本語UI時: 「表示言語」
- 英語UI時: "Language"

**コード例**

```swift
// SwiftUIのText()は自動ローカライズ対象
Text("保存先ディレクトリ")
Text("JPEG品質")

// 変数で文字列を扱う場合
let label: LocalizedStringKey = "メニューバーにアイコンを表示"
Toggle(label, isOn: $showInMenuBar)

// 動的パラメータを含む場合
Text("\(count)個のファイルを保存しました")
```

## ３．非機能要件

### 3.1 パフォーマンス

| 項目 | 目標値 | 根拠 |
|------|--------|------|
| ホットキー押下→キャプチャモード開始 | 0.5秒以内 | Jakob Nielsenの応答時間ガイドライン（1993）によると、0.1秒以内は「瞬時」、1秒以内は「思考の流れが途切れない」範囲。ホットキー操作はユーザーの作業を中断して行うため、1秒の閾値を十分に下回る0.5秒を目標とする |
| キャプチャ実行→ファイル保存完了 | 1秒以内 | ScreenCaptureKitはQuartz Compositorレベルで動作し、macOS標準のスクリーンショット機能と同等のパフォーマンスが期待できる。サードパーティツールでも中央値312msのレイテンシとの計測報告があり、ネイティブAPI＋PNG書き込みで1秒以内は十分達成可能 |
| アプリ常駐時のメモリ使用量 | 20MB以下 | Swiftネイティブアプリはランタイムがシステム組み込みのため、.NET Self-contained（100MB超）と比べて大幅に軽量。macOS上のサードパーティスクリーンショットツールの常駐時12〜28MBを参考に、ネイティブアプリとしてより低い20MBを目標とする |

> **参考文献**
> - Jakob Nielsen (1993) "Usability Engineering" — 応答時間の3つの閾値: 0.1秒（瞬時）、1秒（思考継続）、10秒（集中の限界）
> - Nielsen Norman Group "Response Times: The 3 Important Limits"

## ４．技術構成

### 4.1 アーキテクチャ概要

| レイヤー | 技術 | 役割 |
|----------|------|------|
| UI層 | SwiftUI + AppKit | 設定画面（Settings形式）、メニューバー（MenuBarExtra） |
| キャプチャ層 | ScreenCaptureKit | 全画面・ウィンドウ単位のスクリーンショット取得。SCShareableContent / SCScreenshotManager |
| 範囲選択オーバーレイ | AppKit (NSWindow / NSView) | フルスクリーン透過ウィンドウによるマウスドラッグ範囲選択UI |
| ホットキー層 | NSEvent.addGlobalMonitorForEvents | グローバルホットキーの監視。アクセシビリティ権限で動作 |
| ファイル保存層 | CoreGraphics / ImageIO | CGImage → PNG/JPEG変換、ファイル書き出し |
| 設定永続化 | UserDefaults / @AppStorage | 保存先パス、デフォルト形式、ホットキー設定等の永続化 |
| ローカライゼーション | String Catalog (.xcstrings) | 日本語・英語の多言語対応。Xcode 15+ の標準機能 |

### 4.2 キャプチャ実装方針

ScreenCaptureKit（macOS 12.3〜、スクリーンショットAPI macOS 14〜）を使用する。WWDC23で導入されたスクリーンショット専用APIにより、ストリーミング不要でワンショットキャプチャが可能。

| モード | 実装方針 |
|--------|----------|
| 全画面 | SCShareableContentでディスプレイ一覧取得 → SCScreenshotManagerで対象ディスプレイをキャプチャ |
| ウィンドウ指定 | SCShareableContentでウィンドウ一覧取得 → SCContentFilterでウィンドウ指定 → SCScreenshotManagerでキャプチャ |
| 範囲選択 | 全画面キャプチャ後、CGImageのcropping(to:)で選択矩形を切り出す。選択UIはAppKitの透過NSWindowで実装 |
| 影の制御 | SCStreamConfiguration.showsCursorやcapturesShadowOnlyの設定、またはCGWindowListCreateImageのオプションで制御 |

> **参考**: ScreenCaptureKit — https://developer.apple.com/documentation/screencapturekit/

### 4.3 グローバルホットキー実装方針

NSEvent.addGlobalMonitorForEvents(matching:handler:)でキーダウンイベントをグローバルに監視する。

- アクセシビリティ権限（AXIsProcessTrusted()）の取得が前提
- 修飾キー（Ctrl, Shift, Cmd, Option）とキーコードの組み合わせで登録済みホットキーと照合
- マッチした場合、対応するキャプチャモードをDispatchQueue.main.asyncで実行

### 4.4 設定画面実装方針

SwiftUIのSettings scene（macOS標準の設定ウィンドウ）を使用する。

- macOS標準風の左カテゴリリスト + 右コンテンツのレイアウトはTabViewで実装
- 設定値の永続化は@AppStorage（UserDefaultsラッパー）を使用
- ホットキー変更はカスタムのKeyRecorder View（NSEventを使用したキー入力受付）で実装

## ６．リスク・課題

| リスク | 根拠・背景 | 対策 |
|--------|-----------|------|
| macOS権限のハンドリング | ScreenCaptureKitの使用にはScreen Recording権限が必須（Apple公式ドキュメント）。権限未取得時はAPIがエラーを返す | 初回起動時に権限リクエストフローを実装し、PermissionServiceで権限状態を一元管理する |
| ホットキーがmacOS標準と競合 | macOS標準のCmd+Shift+3/4/5はシステムレベルで予約されており、アプリ側で上書き不可 | デフォルトをCtrl+Shift+3/4/5とし、競合を回避する |
| 範囲選択UIの実装複雑性 | SwiftUIにはフルスクリーン透過オーバーレイの標準機能がなく、AppKit（NSWindow/NSView）との併用が必要 | AppKitで透過ウィンドウを生成し、マウスイベントを処理する。OSSプロジェクト（Capso等）の実装を参考にする |
| Swift 6のstrict concurrency | Swift 6ではconcurrency checkingがデフォルトでstrictになり、@Sendableやactor分離が必要。ScreenCaptureKitの非同期APIとの組み合わせでコンパイルエラーが出やすい | Swift Concurrency（async/await、@MainActor）を正しく適用する。Xcode上でconcurrency warningを都度解消する |
| SwiftUIのmacOS固有の制約 | SwiftUIはiOS優先で発展してきた経緯があり、macOS固有のUI（例: カスタムNSMenuの細かい制御）はSwiftUIだけでは困難な場合がある | 必要に応じてNSViewRepresentable / NSWindowを使い、AppKitにフォールバックする |
